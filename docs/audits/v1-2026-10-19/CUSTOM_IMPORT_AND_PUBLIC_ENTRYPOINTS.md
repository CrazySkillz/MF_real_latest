## Propagation and misleading validation contract

1. All upload/inbound handlers persist normalized data and call `recordCampaignMetrics`; low confidence only adds metadata/log warnings. Webhook response offers `/campaigns/:id/review-import/:metricsId`, but no such React route is registered in `App.tsx`.
2. Latest API selects only `uploadedAt DESC LIMIT 1`, with no `requiresReview` filter. Client `custom-integration-analytics.tsx:2806-2822` truthfully displays **Needs review**, but constructs `scopeType='latest_validated_import'` for that same row.
3. Metric resolver at 345-378 checks numeric availability, not validation state. Fixture proves a review-required clicks value is available. KPI/Benchmark current/progress and Insights use these resolved values; Insights confidence is lowered, rather than values quarantined. Do not claim the UI hides its warning.
4. `scheduler.ts:120,360,437-467,698-729` reads the latest import and uses available values in aggregate/snapshot paths. Missing numeric input is coerced in some aggregate paths; it is not proof of a measured zero.
5. `report-scheduler.ts:575-729` checks campaign/integration scope, then reads latest metrics without review-state filtering. It labels a report window but the imported metrics have no reporting-period dimension. It does not establish that they describe that window. Report metric formatting uses USD. The helper check does not by itself prove live delivery.
6. Executive route `routes-oauth.ts:32969-33079` also reads latest import; actual imported field presence controls web-provider selection. Full diagnostic formulas and alert behavior are separate remaining review tasks.

These are code-confirmed paths, not a complete artifact comparison. Published summaries can consume review-required or silently truncated values; “latest validated” source naming is not a validation gate.
