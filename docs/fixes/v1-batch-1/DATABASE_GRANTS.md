## Confirmed cause and correction

The initial Batch 1 `assertServiceAccountResourceAccess` accepted only `SERVICE_ACCOUNT_RESOURCE_GRANTS` entries. Ptomo has one existing active shared-service-account GA4 connection; without an environment grant that new guard would reject its reads and refreshes after deployment. Google OAuth settings do not authorize that different shared-account path. The preceding `4550381b` correction made customer Google sign-in the creation default, but did not migrate Ptomo's existing connection.

The same storage guard now also accepts an independently reviewed permission from `service_account_resource_grants`. It continues to require the current campaign and client to share the exact owner and the grant to match **owner, client, provider and resource**. No permission is inferred from an existing connection, a submitted property ID, a customer login or the shared credential's ability to read a resource. The optional environment grants remain backward compatible.

Runtime changes stay in [storage.ts](../../../server/storage.ts) and [schema.ts](../../../shared/schema.ts). [Migration 0023](../../../migrations/0023_service_account_resource_grants.sql) creates an empty internal table with a unique exact-scope index and client-delete cascade. It grants no resources. There is no customer-facing grant API, automatic grant writer or new framework. Request handlers and scheduled credential hydration still use the same existing storage guard. Shared credential issuance, provider allowlists, OAuth, response contracts, metrics and analytics transformations are unchanged.

## Lifecycle, rollback and remaining validation

No automatic backfill runs at startup or during customer requests. Database permissions are internal operator records; revocation requires deleting the exact permission and removing any separately configured matching environment grant. The guard does not cache permission decisions. Provider allowlists remain additional requirements. Changing campaign/client ownership or selecting another resource does not inherit the old permission. Client deletion cascades only its own grants; missing/deleted campaigns fail before resource access. OAuth remains independent of both grant stores.

Migration 0023 is additive. Application rollback retains both 0022 and 0023; do not destructively remove schema or other grants. The exact inserted grant can be revoked independently if required. Restore procedures must preserve this authorization table with the rest of the database; comprehensive backup/restore certification remains Batch 8. No permission-table contents or customer identifiers are shipped in the application source.
