## Startup, migration, restart and data protection

`server/index.ts:257–262` accepts HTTP before a five-second delayed migration callback. The first migration group is a sequence of individually awaited DDL/DML statements, without a wrapping transaction, version ledger or startup advisory lock. Failure at1098 logs a warning and exits that group; later independent migration groups, demo seeding1198 and every scheduler start still run. `/health` and `/api/health` at `routes-oauth.ts:796–810` do not check schema or migration status. Consequently neither healthy HTTP nor successful later DDL proves the full required schema. V1-007/009 remain confirmed; concurrent/upgrade migration correctness is unverified until isolated full-schema boot exercises are run.

The startup writes are not DDL-only: `index.ts:790` normalizes nullable Sheets flags;956 resets connected Facebook/LinkedIn integration rows;84–165 seeds global demo tables and campaign facts. These execute on ordinary production startup under the current conditions. Do not call the migration group idempotent merely because many statements contain `IF NOT EXISTS`. Unique indexes can fail on historical duplicates, and partial progress survives the first error. No migration was run against deployment during this audit.

Unhandled rejections and uncaught exceptions at `index.ts:195–207` are logged while the process remains alive. No SIGTERM/SIGINT drain handler, scheduler stop orchestration or pool shutdown call was found in tracked non-test server code. Native GA4 durable leases/recovery reduce only their own interrupted-work risk; they do not cover pending OAuth, ordinary paid imports or all report sends. OAuth Salesforce PKCE and Shopify nonce state (`routes-oauth.ts:7252`,11546,11792) and GA4 pending property selection (`global.oauthConnections`) are process-memory state. Restart or another replica can require reconnect; a real interrupted/replayed callback test is still needed. GA4/Sheets/HubSpot signed state has expiry and campaign-owner callback checks; nonce presence alone is not a proven single-use replay defense.

`db.ts` bounds connection acquisition10s, statements120s, queries125s and idle transactions120s. It uses `rejectUnauthorized:false` for `sslmode=require` (V1-008). These are read code settings, not measurements of production pool size/saturation/TLS identity.

`utils/tokenVault.ts` uses AES-256-GCM with random12-byte IV/auth tag and versioned ciphertext. The low-level key resolver still accepts SESSION_SECRET/APP_SECRET and a known development fallback. Explicit production-key assertion is present in Shopify, GA4 Google Ads Spend and some related writes (`storage.ts:4174,4200,4254,4273,4327,4943,5087`), but is not universally invoked by all connection writes. V1-008 must be fixed/verified by path, not stated as absence of all safeguards. Key rotation compatibility, production key presence and restored ciphertext decryption remain unverified.
