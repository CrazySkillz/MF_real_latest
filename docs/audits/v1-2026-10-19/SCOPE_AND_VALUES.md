### Lifecycle through the supported journey

1. `App` -> Client context -> client APIs -> `storage.getClients/createClient/deleteClientCascade`. Owner filtering is present in client queries. Deletion is not recoverable through a UI undo. Current campaign insert and client enumeration are separate from client deletion's transaction; an authorized concurrent insert can orphan a campaign (V1-023). Restore is an operational gate, not assumed recovery.
2. Wizard -> `POST /api/campaigns` (9037) creates owner-bound draft; selected Client is checked before `storage.createCampaign`. `PATCH` (9137) accepts/recovers async initial imports; `DELETE` (9261) separates unsubmitted draft cleanup from accepted work. Native durable work owns imported properties and activation. Source setup “Ready/Selected” versus final “Connected,” Back navigation, interrupted request and reload remain live browser checks; local P4/P7 tests only cover their fixtures.
3. Connection -> exact campaign owner -> selected property/account/sheet and filter -> source config + materialized records. OAuth, service account and retained token/test modes are separate configurations. A connection row is not proof of permission or complete import. Empty selection must fail closed. Changing selected source requires invalidating prior snapshots and blocking stale writes, not displaying a mixed revision.
4. Readiness/saved publication -> GA4 overview -> financial and traffic helpers -> KPI/Benchmark current values/history -> Insights/diagnostics -> notification decisions -> browser/server report artifacts. A last-good value can stay visible with stale state; it must not masquerade as a fresh zero. Source mutation and refresh require the entire downstream matrix below.
5. Edit/delete/reconnect -> exact source or child scope -> durable transaction -> recompute/invalidate -> stable source list -> downstream publication. No destructive live scenario was run. Concurrent source edit/delete tests and real PostgreSQL publication tests provide bounded evidence, with the failing mocks retained in the ledger. Existing corrupted/demo/legacy rows need read-only damage classification before cleanup.
