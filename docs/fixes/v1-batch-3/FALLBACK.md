# Emergency application fallback

This branch is a recovery target for the completed Batch 3 changes in `001ddfa87c445a51e63320cde9737b774aa1af0c`, not a V1 release certificate. The other audit records on this branch are inherited historical records. Current evidence and the release decision are maintained on `main` in `docs/fixes/v1-batch-3/README.md` and its `deployment-2026-10-22` evidence folder.

It restores the previously deployed `839bf508bffea4742f992616753dc68eabcfab3e` behavior except for the complete fractional-conversion correction: parsing, decimal reconciliation, schema migrations, startup, stored current/history values, calculations, displays, alerts and reports retain the corrected precision. Batch 1 and Batch 2 changes are retained. Other Batch 3 corrections (query matching/pagination, native total-query cancellation, revenue source identity/refunds and currency invalidation) are absent, with their known findings still open. This is a bounded emergency fallback, not a claim that those original defects are safe for general release.

Use only for a confirmed deployment incident after checking that its recovery scope addresses that incident. Deploy this exact fallback commit, or cherry-pick its single fallback commit onto the deployed candidate only after confirming the runtime still matches `001ddfa8` and the cherry-pick is conflict-free. Do not merge it as routine forward development. Keep the widened database columns and constraints; do not downcast values or overwrite newer data with the backup. Roll forward to the tested main candidate once the incident is resolved.

The startup and precision migrations are byte-equivalent after newline normalization to the candidate tested against the restored production backup. Independent fallback builds, synthetic/localhost regression tests and startup/restart tests are recorded on `main`. Providers and worker bodies are stubbed during local startup tests. Hosted recovery execution and whole-app release acceptance remain separate gates.
