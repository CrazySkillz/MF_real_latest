## Daily input and calendar boundary

`client/src/pages/ga4-metrics.tsx:1965` reads the selected property's `/ga4-daily?days=60&readOnly=1`. The query verifies HTTP success and property identity, but does not reject incomplete scheduler coverage. `trendsCampaignStartDate:2107` uses campaign creation in the reporting timezone. `trendsDailyRows:2115–2125` filters supplied rows to creation through the completed-day cutoff, then fills every absent date in that whole calendar interval with zero. Both Trends and Findings consume these rows (`findingsDailyRows:5240`).

In the real-data final branch of `server/routes-oauth.ts:9540`, failure of the first daily-window storage read is caught as an empty array. A separate full-import-window read can succeed, allowing a response with `success:true`, positive Overview totals, empty daily data and `schedulerCoverageComplete:false`. The client accepts that response and manufactures a complete sequence of zero-valued dates. This differs from an HTTP failure: the latter produces an explicit unavailable-history finding, but this successful-response fallback bypasses it.

The shared `buildGA4InsightsRollups` helper in `shared/ga4-insights.ts:227–355` deduplicates dates, sorts them, sums sessions/pageviews/conversions/revenue, weights engagement, calculates conversions/sessions and pages/session, and requires an exact adjacent-calendar day count for completeness. This guard operates on already padded client rows; it cannot distinguish verified zero activity from failed/unfetched/missing dates. `buildGA4InsightsMonthlySeries:357–394` similarly counts supplied dates to determine partial months. The Trends UI at9531–9578 passes the padded interval, which may extend far before the API's60-day request.

**V1-077, three exact-code reproductions:** [results](insights-calendar-reproductions.json), [runner](insights-calendar-reproductions.cjs).

Storage/freshness decoration are controlled fixtures; normal authentication, provider selection, React rendering and scheduled PDF generation are not executed. No production data read/write was needed. A known empty provider day may legitimately be zero, but that requires independent successful coverage evidence. Failure or absence alone is insufficient.

## Finding policy and value inventory

Severity sorting is high→medium→low, preserving insertion order for ties. Category grouping is setup, targets, trends, finance, context. Confidence labels at5219 are fixed policy: integrity/finance high,3-day low, other trend/target medium; they are not statistical confidence calculations. Data-basis labels at5200 explicitly describe campaign-creation daily history and zero-filled no-activity dates; they cannot prove those dates were actually observed.

`insightsActionDescription:6052–6069` reports days/expectedDays and complete-window status from the same rollups. The tracker at9935 counts all severity findings; the UI at9973 shows the first12 and explicitly reports the remaining hidden count. Categories filter that selected12, not independently12 each. Each card carries basis, confidence, description and recommended check. The browser PDF at4488–4564 uses the same description and finding metadata. Thus correcting only a chart label would leave false coverage and recommendations in other consumers. Saved/scheduled reports need independent artifact-value checks; browser reuse is not proof of server parity.

## Design alignment, lifecycle and remaining checks

`GA4/INSIGHTS.md:107–113` explicitly describes the60-day read, creation-date filter and legacy sparse-date zero filling;161–163 permits last successful scheduler data despite refresh staleness. The implementation therefore aligns with that documented intent. **The defect is the missing distinction between verified no-activity and failed/unfetched dates**, including time before the requested range. Design text cannot establish truthful coverage. Preserve the existing journey while defining the supported daily-coverage contract during the agreed fix batch. Financial imported-window totals intentionally have a separate window contract; do not assume they should equal daily native trend revenue.

All rows are recomputed in browser memory after query changes; they do not themselves persist source facts. Connection/property/filter changes, source edits/deletes, refresh failures and recovery affect upstream responses and target histories. Relevant source lifecycle findings remain in their detailed records. Required acceptance includes query failure with retained versus absent data, sparse/zero provider dates, campaign older than60 days, creation after import, timezone/DST boundaries, adjacent-window cutoffs, property changes, multiple/imported revenue sources, every finding threshold/tie, negative/zero baselines, target list/history failures and browser/saved/scheduled PDF parity. The three cases prove the identified failure boundary, not all those combinations.
