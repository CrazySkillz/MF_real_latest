## Access and safety boundary

The repository `.env` supplies a remote database connection. The reader uses the installed PostgreSQL driver directly, with TLS certificate verification enabled, a five-second connection/statement timeout and eight-second client query timeout. It opens **REPEATABLE READ READ ONLY**, verifies `transaction_read_only=on`, uses parameterized exact-name/campaign-ID predicates and rolls back before closing. It does not import the application, storage getters, schedulers or provider clients, so it cannot trigger lazy credential migration, source refresh or startup seeds. All table names are fixed reviewed schema names. No mutation, test-send, provider request, load test or redundant-campaign inspection was performed.

Exactly one case-insensitive, trimmed `Ptomo` match was found. Only that campaign's selected metadata and reconciliation booleans were recorded. Raw credentials, provider/property IDs, campaign ID, account owner ID, client name and business metric amounts are omitted; the campaign ID is represented by SHA-256 solely for evidence identity. Credential checks selected presence booleans, not secret columns. The actual authenticated UI owner/session was not established by this SQL check.

**Database/deployment binding is unverified:** this proves state in the repository-configured database. It does not independently prove Render uses this same database or configuration. The earlier public health revision remains a separate observation. No available connected browser is authenticated, so fresh UI/API/Clerk behavior remains externally blocked.

## Audit-reader corrections

The first environment inspection attempted an unavailable dotenv package; no network request or database query happened in that attempt. The reader uses Node's built-in parseEnv without adding a dependency. Initial PostgreSQL timestamp-without-time-zone values were interpreted by the Windows driver's local timezone. Before drawing freshness comparisons, the reader was corrected to preserve type1114 as raw database strings and rerun. Explicit timestamptz values remain UTC instants; database session timezone was observed asUTC. This is an audit-reader correction, not a production timestamp defect. The linked final JSON is the authoritative observation.
