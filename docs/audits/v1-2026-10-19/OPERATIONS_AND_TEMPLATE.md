### V1-089: current Insights provider fan-out is not bounded by property quota

`server/analytics.ts:2339–2372` collects every landing-page source/medium pair and uses one unbounded `Promise.all` to fetch each channel. The current `requestReport:47–88` adds retries/deadlines, not a property-wide concurrency queue. This is reached by the current Insights breakdown query (`routes-oauth.ts:13736`, `ga4-metrics.tsx:2139–2164`); native scheduled Overview uses a different flag and is not attributed this particular fan-out.

[Three exact-service fixtures](ga4-concurrency-reproductions.json), [runner](ga4-concurrency-reproductions.cjs), measured2 channels/one reader→2 concurrent channel calls;12 channels/one reader→12;12 channels/two readers→24. The latter scenarios dispatch14/28 total provider requests including base/discovery queries. None requested property-quota response metadata. All transport responses were local fixtures; no provider load or real429 was induced.

Google documents a Standard property's Core concurrent limit of10, with separate property/project token and server-error quotas; Analytics360 has a concurrent limit of50. Token cost depends on query complexity, and `returnPropertyQuota` exposes consumption/remaining quota. These are not a per-user60-requests/minute contract. [Official GA4 Data API quotas](https://developers.google.com/analytics/devguides/reporting/data/v1/quotas).

`middleware/rateLimiter.ts:78` defines a60/minute GA4 limiter, but tracked non-test code only imports it at routes893; no route mounts it. `generalApiRateLimiter:93` has no runtime import/mount found. Other OAuth/LinkedIn/import/Sheets limiters are mounted on selected routes, and three accept the client-controlled test-mode bypass in V1-053. Even a mounted per-IP HTTP limiter would not bound this one request's internal channel fan-out or coordinate replicas sharing one provider property.

Required acceptance: bound current provider work within the existing service/scheduler flow, identify quotas per property/project/source, preserve failure/unavailable states, and exercise retry/cancellation plus concurrent readers/jobs. The user delegated conservative realistic figures: five simultaneous users and25campaigns. The later actual HTTP pilot established5,000rows as the Revenue UI limit, with10,000rows tested as oversize; the earlier10k computation is parser-only evidence. [The isolated component load check](PILOT_LOAD_CHARACTERIZATION.md) passed its stated local thresholds; it does not certify whole-application/deployed throughput or live quota recovery. Production deployment/proxy topology and actual property tier remain externally unverified.

## Reusable architecture and future-source acceptance template

This is a template for validation within the **existing architecture**, not a new framework and not permission to implement Instagram, TikTok, Meta or any source now.

Verified reusable **patterns**, with their evidence boundaries:

- Preserve Client -> campaign -> selected main platform -> child financial source journey. UI stays under client/src, endpoint orchestration in routes-oauth.ts, persistence/transactions in storage.ts, contracts in shared/schema.ts, jobs in existing scheduler/service files. Current declarations prove this structure, not every branch's correctness.
- Require actor/owner at the route and recheck exact campaign/source/config identity at durable write. Native GA4 publicationVersion/lease/fingerprint checks have current isolated PostgreSQL regression evidence (`ga4-refresh-*`, `ga4-snapshot-ownership-postgres`, initial-import/publication tests). Reuse their fail-closed principle only after adapting the new source's write paths; external financial sources do not yet inherit full native recovery.
- Materialize exact source records transactionally; distinguish add-another from replace-one; preserve last-good data on failed replacement. Revenue aggregate-versus-attributed grain and currency helpers have explicit tests. Current mock failures in transaction/deletion families must be repaired before treating those entire operations as accepted templates.
- Keep authoritative availability/freshness/provenance alongside values. Zero and negative amounts are finite data; missing permission, incomplete query, invalid currency and absent source are unavailable, not0. Formula inputs and source IDs must match cards, source modals, KPIs/Benchmarks, Insights/diagnostics and artifacts.
- Bound pagination and reject incomplete responses. Preserve scope in every fallback; exact join keys only; no guessed allocations. Current HubSpot/Salesforce/GA4 helpers provide test examples, but GA4 acquisition missing-rowCount behavior remains an open negative-case gap.
- Use stored publication/coverage evidence to align readers and scheduled artifacts. Internal loopback authentication, report parent/snapshot checks, report-ID deduplication and dismissed-versus-resolved notification history are reusable tested constraints. Report retry claiming and artifact persistence defects identified here must be fixed before copying them.
- Maintain source-specific damage inventory and separately approved exact cleanup, immutable evidence, isolated fixture negatives and current-commit acceptance. A prior readiness statement is never an input to the proof.

Confirmed current defects are **not reusable implementation examples**: integer truncation of fractional GA4 conversions (V1-079), ignored provider quality metadata (V1-090), unbounded per-channel request fan-out (V1-089), stale currency-labelled daily rows (V1-087), destructive reconnect/transfer paths (V1-037/069), report retry/delivery/artifact gaps (V1-021/022/058/059) and draft creation/cancellation gaps (V1-091–093). GA4's conditional token-migration update is a positive stale-write control; other tested getters lack it (V1-088). New providers need separately proven credential refresh/migration behavior, not only encryption at rest.

GA4-specific assumptions that **must not be copied blindly**: property ID and sessionCampaignName/campaignName/firstUserCampaignName/pageLocation scopes; UTM campaign matching; totalRevenue/purchaseRevenue fallback; totalUsers daily aggregation versus unique-period users; fractional attributed key events versus ad conversions; engagedSessions/session denominator; fixed importStartDate; completed-day/property-reporting timezone; GA4 currency conversion and response-quality metadata; native-only publication lease eligibility; GA4's lack of spend; exact landing/event/geographic grains and API rowCount behavior; per-property/project/token/error quotas and Standard versus360 concurrency. Meta placement/action attribution, Instagram publisher filtering, TikTok advertiser/live API capability, Google Ads cost micros/manager accounts and CRM deal/opportunity stages require independent contracts.

For every new source, fill the same scope/value/propagation matrices and provide regression cases for permissions/OAuth/revocation, tenant and selected-account isolation, native metrics and attribution windows, dates/DST/partial days, currency/precision, all pagination/quota/rate-limit behavior, source add/edit/delete/reconnect/list/refresh/reprocess, restart/concurrency/timeout cancellation, persisted-data integrity, zero/missing/stale states, formulas, snapshots, alerts and browser/server reports. Current local proofs are reusable test examples; no source receives certification by inheritance.

The user's [four-provider deferral and Ptomo selection](UNCONFIGURED_SOURCES_AND_PTOMO.md) control current acceptance scope. Unconfigured providers are not being implemented or functionally certified. The V1-121 isolated cases show that hiding onboarding and removing credentials does not disable simulated connection APIs/jobs. Future activation needs explicit production/test isolation. The [V1-122 decision fixtures](source-goal-alert-reproductions.json) also show that GA4's current-value/freshness decision helper does not automatically resolve Custom/Sheets source-backed goals. Future sources need independent evidence that the current UI, stored goal, notification decision and email decision use the same saved source identity and authoritative value.
