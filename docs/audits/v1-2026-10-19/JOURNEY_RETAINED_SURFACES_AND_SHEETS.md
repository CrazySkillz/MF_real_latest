## Account → client → campaign creation/edit/cancel/delete

The protected `App.tsx` route branch and Clerk gate include the alternate Clients/Dashboard/Audiences/KPI/platform pages. Selecting a client in `clients.tsx:17–19` navigates to `/dashboard`; the primary home journey navigates to Campaigns. That alternate path is reachable and leads to global data (V1-002); hiding it in navigation does not exclude it.

The wizard in `campaigns.tsx` persists a draft before final creation. Final Create sets `initialImportRequested` before sending PATCH648–660. A failed HTTP response triggers status re-read rather than deletion of potentially accepted work. It polls initial import every3seconds and draft list every5seconds, supports reopening failed/saved setup, and routes Back using recorded previous step696–714. Closing while the final request is in flight is blocked. Closing before acceptance calls guarded draft cleanup; afterward it preserves the accepted campaign (`handleCreateModalChange:880`). Cleanup errors are ignored, so an interrupted/failed draft cleanup can leave a draft rather than guaranteeing removal. These are code traces, not a fresh-account browser certificate.

`PATCH /api/campaigns/:id`9136 checks actor ownership and target client ownership, strips ownerId, validates schema and distinguishes draft activation. It persists native GA4 initial-import work before202, refuses unsupported configuration and returns the completed state for a lost-response retry. A previously accepted import prevents ordinary activation from bypassing it. Filter/timezone changes use `updateCampaignWithGA4DailyInvalidation`; ordinary updates still invalidate native refresh identity. Native saved readers/publication guards must independently reject incompatible currency/property/scope after edits; this does not automatically reprocess imported file/CRM records.

`storage.deleteCampaignCascade:841` locks the campaign, verifies draft-owner/status when cleanup is requested, refuses cleanup of an accepted initial-import work item, then deletes children and parent transactionally. `deleteCampaignChildren:732–838` enumerates KPI progress/alerts/periods, Benchmark history, LinkedIn import metrics/ads, reports/send events/snapshots, AB-test children, all financial source/record families, provider daily facts/connections (including Instagram/TikTok and optional GA4 Ads Spend), Custom Integration/conversion rows, KPIs/Benchmarks/snapshots and attribution rows. Notifications are soft-hidden; email audit rows are deleted within that campaign. Tables without enforced FK relationships and concurrent child writers need their own race tests; parent locking protects only writers that participate in the same protocol. V1-023 already reproduces concurrent client-delete/campaign-create orphaning against PostgreSQL. No production cleanup was performed.

Recovery acceptance remains explicit: draft abandonment/reload, OAuth denial or restart, lost final response, import retry, source edit/delete during refresh, parent deletion during report/alert sending, and existing damaged-data inventory. A transactional delete is not evidence all concurrent providers fail closed.

## Google Sheets Revenue: independent from Spend and standalone Sheets

`routes-oauth.ts:5442` authorizes campaign, exact connection/source identity and GA4 mapping. Add means a new additive source; edit requires the supplied active source ID/type/context. Connection fallback remains inside the same campaign and selected spreadsheet, but can substitute another connection's credentials after401. It retries token renewal, then requests tab metadata and bounded full-row chunks (`readGoogleSheetsRevenueChunks:3149`). `google-sheets-revenue-ranges.ts` selects the exact named tab or first visible tab, requires a positive integer grid row count, reads5000-row chunks and rejects grid sizes above50000 including header. These safeguards are stronger than GA4 Spend's fixed5000 range and standalone Sheets'1000 range; do not attribute those truncation findings to Revenue.

Selected revenue rows require strict numeric syntax and valid mapped dates; missing campaign selection is rejected. Exact campaign value matching, daily totals and optional attributed records are separate from aggregate financial grain. Only positive rows are materialized; all-zero input is rejected. Undated rows are assigned the latest completed campaign day. Mapping currency must equal campaign currency. Source-to-date and completed-day amounts are both returned, with different meanings.

**V1-065:** headers at5609–5620 become object keys without a uniqueness check. Fixture headers `[Revenue,Revenue]` with values `[100,7]` silently persist7. The first amount is overwritten before strict amount validation; no downstream source/total guard can recover it. Strict CSV Revenue explicitly rejects duplicate headers in `utils/csv.ts:422–425`, so this is a code-path inconsistency, not a universal parser claim.

**V1-066:** `google-sheets-revenue-amount.ts` permits `$` independently of currency; process1456 strips it and5719–5731 validates only mapping currency versus campaign currency. Fixture `$100` in an EUR-mapped EUR campaign succeeds and persists100EUR. No conversion or dollar-currency proof occurs. The malformed `12oops` control rejects400 before persistence, so the finding concerns currency semantics rather than a claim all syntax checks are absent.

The GA4 process uses `replaceRevenueSourceWithRecords` transaction5774 with expected old mapping for edits. Post-commit derived recompute failure is logged and import still succeeds; freshness/publication and later retry must be verified across all consumers. The in-flight add guard is a process-local Set and is removed in finally, not a durable request identity. A retry after a lost successful response or two replicas can create two additive sources. User-intended second imports and retries must remain distinguishable before adding idempotency; no blanket deduplication/cleanup is authorized. Non-GA4 branch deletes prior records before insertion and does not inherit the GA4 transaction guarantees.

Source delete helpers `storage.ts:1906,2383` transactionally deactivate the exact active campaign/context source, delete its exact records and return actual row outcome; GA4 also fences refresh ownership. Full disconnect separately checks shared connections and other source contexts before removing credentials. These forward-path traces do not validate every refresh/delete race or existing damaged rows; the current failing transaction fixtures remain open.

**V1-067:** scheduled Revenue refresh is an independent implementation (`auto-refresh-scheduler.ts:488–694`). It uses the same bounded tab/chunk and strict amount helpers but only reads `mappingConfig.campaignValues`, ignoring singular `campaignValue` supported and preserved by the save route. [Two exact refresh fixtures](sheets-refresh-reproductions.json) prove singular selected10 becomes all-rows100, whereas array selection remains10. This is a persisted-data corruption boundary: fix forward selection first, then read-only inventory affected stored mappings/records before any targeted cleanup. It also maps untrimmed raw headers, whereas the save route trims headers; malformed/changed headers must preserve last-good data and expose failure. Refresh token writes carry expected-connection identity; final record replacement compares saved mapping and carries optional refresh ownership. These safeguards do not correct the missing filter.

Fixture integrity: the first Sheets Revenue runner selected a different nested `parseNum` during source extraction and failed its dollar case. The audit runner was corrected to bind the actual outer handler helper at1456, then all3cases passed. No runtime change was made. That harness failure is not counted as an application test failure or silently used as product evidence.

## Retained manual financial paths

GA4 manual Revenue rejects contextga4 after owner/schema checks4540–4552. Non-GA4 Revenue accepts positive amount or LinkedIn conversion value, writes a manual source, deletes previous records and materializes a yesterday-UTC total. Conversion-value mode updates connection/latest session and deliberately creates no revenue records; edits can change another type of source to manual because only campaign/context is checked. These operations are multi-step rather than the GA4 transactional replacement path. Currency is configured, not converted; old dates/source provenance and failed intermediate writes need explicit retained-path acceptance.

**V1-068:** manual Spend6010 checks the effective type, which `spendSourceTypeForPlatformContext:5953` accepts from the caller. The [three handler fixtures](manual-spend-reproductions.json) prove normal GA4 manual rejection, relabeling a manual100 amount as CSV successfully, and non-GA4 record-insert failure still returning success. Dedicated Google Ads Spend has its own connection/selection/materialization checks; sourceType=csv bypasses that branch too. Records are assigned current UTC date. Thus GA4 manual exclusion is not fully enforced by the route, and source labels do not always prove provenance. Non-GA4 manual writes swallow delete/insert/recompute errors and can leave mapping-only or doubled data. Preserve the exact source/type/owner boundary when fixing and validate downstream totals/list/refresh/report behavior independently.
