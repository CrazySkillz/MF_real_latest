## V1-124 — unsafe scheduler delay and startup configuration

**P1, exact isolated reproduction.** `google-ads-scheduler.ts:398–410`, `google-sheets-token-scheduler.ts:168–207`, `scheduler.ts:862–900`. [18 cases and five actual Node normalization controls](scheduler-configuration-reproductions.json), [runner](scheduler-configuration-reproductions.cjs).

For Ads/Sheets, zero, negative, nonnumeric and excessively large hour strings become invalid setInterval delays. Node normalizes each tested invalid delay to1millisecond. An unknown SNAPSHOT_FREQUENCY indexes an absent delay and also becomes1millisecond. Defaults and each supported snapshot frequency pass their controls. These jobs can repeatedly perform DB/provider work; this audit intercepted every job and timer and did not run a rapid loop.

Two Ads starts create two intervals. Sheets only sets its global running marker after the delayed first run; two starts before then each perform an initial refresh and register their own timeout/interval. Snapshot repeated-start control correctly retains one interval. Multi-process ownership remains a separate issue even after correcting same-process startup.

Required fix: validate/fail closed or bound settings in existing scheduler starts, reserve the running handle before asynchronous startup, and prove stop/restart plus invalid inputs without actual production traffic. Do not introduce a scheduler framework. No current deployed invalid setting or duplicate boot is claimed.

## V1-057 supplement — provider errors expose credentials to logs

`googleAdsClient.ts:75–91` attaches Bearer/developer-token headers. `routes-oauth.ts:27154–27175` logs the complete error object when Google Ads refresh fails. [Three exact-client/handler fixtures](provider-error-log-reproductions.json), [runner](provider-error-log-reproductions.cjs), use real Axios with an in-memory adapter and synthetic credentials. Normal console formatting of its thrown AxiosError includes both headers. The HTTP response does not include those marker values; denied-campaign and successful-response controls make no secret log entry.

The fixture substitutes the scheduler dispatch with the actual client account read; current scheduler code propagates that error. This proves the log serialization boundary, not production compromise or every provider catch path. V1-057 now includes both Custom bearer/body logging and raw provider error objects. Review/redact credential-bearing error/request fields in affected paths; any real exposure inventory and targeted credential rotation is separate, authorized work.

## Backup/restore exercise and its limits

[Result](backup-restore-fixture.json), [runner](backup-restore-fixture.cjs): PostgreSQL18 on disposable loopback55443;62 generated tables, six populated tables,12 rows across two synthetic owners. Exact current tokenVault encrypted synthetic tokens using an ephemeral random key. Custom-format pg_dump, verified fixture-schema drop and pg_restore restored identical row hashes, original-key decryption and PDF bytes. Wrong-key controls returned null credentials. The [dump](synthetic-backup-restore.dump) contains only synthetic fixture data; no application key or customer dataset.

This proves a local logical-backup procedure and the need to recover the compatible encryption key. It does **not** prove production backups/PITR, hosted permissions, key escrow, recovery timing, actual snapshot-renderer behavior, deployment rollback or post-restore jobs. The fixture's PDF container is intentionally synthetic. Production's observed PostgreSQL17.9 differs from the local18 environment. Production database+key recovery and prior-image/schema compatibility remain required external acceptance.

All random schemas were removed and both disposable PostgreSQL instances stopped. Initial harness rejected a legitimate fixture table name containing digit4; its finally block removed that schema before retry. That was a harness validation correction, not an application finding.
