## Source → API → calculation → UI inventory

1. GET /api/campaigns/:id supplies owner-scoped campaign budget, pacingStartDate, pacingEndDate, currency and reportingTimeZone; the page renders them in Budget Position and the pacing form. PATCH /api/campaigns/:id is protected by ensureCampaignAccess, validates through insertCampaignSchema.partial(), strips client-supplied ownerId, writes through storage.updateCampaign, and returns the updated row. The page sends only budget and pacing fields for Save/Delete, inserts the returned row into query cache, then invalidates campaign and outcome queries. Delete sends all three fields as null. Add/edit/delete are code-traced, but no deployed mutation was authorized in a read-only pass.
2. GET /api/campaigns/:id/outcome-totals?dateRange=90days is campaign-access guarded. For the deployed GA4 path, its v3 currentValueWindow overrides the apparent 90-day query for current financial values: native GA4 is property/import-start to latest completed reporting day; active GA4-context imported revenue and spend records use 1900-01-01 to that same end day. The route builds financialInputs and calls buildCampaignPerformanceSummaryAggregate; the page reads performanceSummary.totals, performanceSummary.sources and financialInputs rather than its old platform sums when the aggregate is present. A non-v3 branch remains in code and is outside the exact-runtime GA4 proof.
3. Storage filters financial rows by campaign, active source, GA4 platform context and date, preserving source IDs and per-source breakdowns. Revenue validates materialized row/source currency against campaign USD. v3 spend rejects a materialized currency unequal to campaign USD. Neither current storage query proves every active source has represented records for the completed-day window.
4. Financial Position displays aggregate spend/revenue; Profit is their difference. ROAS/ROI/CPA are aggregate calculations, not local page estimates in the observed path. Conversion Efficiency appears only when v3-window-gated aggregate CVR is available. Paid Media Efficiency appears only when a compatible v3 CPC, CPM or CTR is available; it displays only available metrics. On the deployed GA4-only campaign all three are unavailable and the heading must remain hidden. Positive paid media appearance is code/test traced only; no deployed paid source fixture was verified.
5. Budget Position uses positive campaign budget, aggregate spend, spend / budget × 100, budget minus spend, and a visual progress bar capped at 100%. Pacing uses inclusive elapsed budget-period days, inclusive total days, spend / elapsedDays, budget / totalDays, their ratio × 100, and thresholds below 85% / above 115%. It also shows an exhaustion projection from remaining budget/current burn and whether that date lies before/after the period end. Budget metadata does not filter the source totals. Date arithmetic uses the browser local day and local-midnight millisecond difference, while the report uses a zoned today and UTC date arithmetic.
6. Allocation & Sources lists financialInputs.revenue and .spend, falling back to aggregate financial source rows for revenue only when the explicit revenue array is empty. Current UI removes rows with values not greater than zero. Executive Action builds one return card, one pacing card and one allocation/source-mix card. The allocation helper uses positive spend inputs only, requires sum-to-Total-Spend within $0.01 before naming a largest source, and otherwise falls back to eligible main-source capability guidance. These are guidance statements, not automatic allocation writes.
7. The visible legacy tabs and their historic charts/cards are behind a constant false renderer. The page still fetches a financial_daily comparison snapshot but renders no current historical comparison card. Separate downstream consumers include scheduled/direct Campaign DeepDive PDF rendering and financial daily snapshots; neither may inherit browser certification. The PDF is built in server/report-scheduler.ts and can be exposed through report routes/schedules. The present PDF positive-path test covers a single-GA4 fixture, not a GA4-plus-paid campaign.

## Blocking findings and dependency impact

| ID | Root cause and demonstrated boundary | Affected outputs and smallest safe fix direction |
| --- | --- | --- |
| F1: zero efficiency | buildPerformanceSummaryAggregate requires totalConversions > 0 for CVR, totalClicks > 0 for CTR and costSpendValue > 0 for CPM, even when the denominator is positive and the measured numerator is valid zero. | Valid 0% CVR hides Conversion Efficiency; valid 0% CTR and $0 CPM can hide Paid Media Efficiency. Correct numerator-zero treatment must preserve denominator availability, source compatibility and campaign-to-date window; add focused zero tests before any shared aggregate edit. This touches Performance Summary consumers, a certified upstream path, so explicit approval is required. |
| F2: zero/negative provenance | Route includes native GA4 financialInputs.revenue only when onsiteRevenue > 0; page filters revenue/spend breakdowns by > 0; allocation helper also filters positive spend. | A valid $0 source and a negative adjustment can affect authoritative totals but disappear from Sources Used. Net-zero/negative source mix and reconciliation become misleading or withheld. Native sign, source labels and aggregation must be preserved in route/UI/report and tested across adjustments; this affects shared financial API and report output, so explicit approval is required. |
| F3: calendar day error | Browser pacing computes local-midnight millisecond differences divided by 24 hours and floors. A DST transition makes a calendar day 23 hours; browser today is also independent of the campaign reporting zone. | Example in Europe/Amsterdam: 2026-03-28 through 2026-03-30 counts two elapsed days and 2026-03-28 through 2026-04-03 counts six total days; correct inclusive calendar counts are three and seven. With $700 budget/$230 spend, UI yields 98.57% On Track instead of 76.67% Behind. Daily burn, target, status, projection and Executive Action change; the PDF uses UTC calendar dates and diverges. Fix only the date-only day calculation and campaign-zone today after approval; test DST, before-start and after-end. |
| F4: incomplete materialization | Spend total/breakdown queries inner-join only existing records. GA4 imported-revenue completeness guard runs only when end date is at least current UTC day, while v3 outcome totals ends at latest completed day. Active sources lacking records can be omitted with another source still present. | Partial source totals can be marked available; Sources Used and return/source-mix guidance then look complete. Fail closed or prove zero-record semantics at the exact active-source/date boundary, with currency and owner checks. This changes source/storage/route behavior and may reveal damaged persisted data; any cleanup needs a separately bounded plan and approval. |
| F5: mixed-source PDF provenance | Report renderer fetches detailed financial input rows only if the aggregate has exactly one main source and it is GA4. For GA4 plus a paid main source, both arrays are empty, yet it labels revenue minus importedRows as GA4 Revenue. | A mixed-source PDF can label all campaign revenue as native GA4 and say no detailed spend inputs exist while the browser has real imported rows. The same renderer serves direct/snapshot/scheduled PDF paths. Must use the already authoritative source breakdown under campaign scope, preserve report contracts and test multi-source parity before approval. Report code is a certified adjacent section. |
| F6: stale success after failed refetch | The outcome query retains previousData; aggregateUnavailable only checks missing performanceSummary, so a failed later refetch leaves the last successful values and actions rendered with no explicit stale/error state. | Financial cards and action copy can appear current after refresh failure. Establish a bounded last-success/freshness rule and visible failure state without replacing valid cached data with false zero. This is code-traced; a controlled deployed outage was not induced. |
| F7: paid-source compatibility | Aggregate cost/CTR calculations use independent spend, click and impression contributor sets; the UI source caption includes any paid source with any of those capabilities. A partially mapped paid/custom source can therefore be named or counted in a ratio without supplying both required dimensions. | CPC/CPM/CTR and Paid Media Efficiency attribution for mixed partial sources are not certified. Align numerator/denominator/source captions to common compatible contributors, or explicitly prove the intended aggregate denominator rule, then test paid combinations and deploy a real paid fixture. This touches the shared aggregate and needs approval. |

Additional bounded limitation: the non-v3 page still accepts aggregate financial metrics while describing them as campaign-wide; v3 gating applies specifically to Conversion/Paid Efficiency and allocation, not every Financial Position or pacing metric. This requires separate source-family/window certification before extending the claim beyond the deployed GA4 v3 path. The existing GA4-only PDF can display CVR among financial metrics without a separate Conversion Efficiency heading; value parity and section presentation should be checked with the report owner if headings are part of the report contract.
